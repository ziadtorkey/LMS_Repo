**Goal (as approved, D23):** Admins create, list, edit, deactivate and share staff with role assignments and activation emails; staff are imported from Excel through one all-or-nothing import framework running as background jobs; a daily job expires staff and warns admins beforehand; clients can sign in through their own OpenID Connect / Azure AD provider; the people kernel already carries the student/guardian data model (no student-facing endpoints or pages) — all bilingual (ar RTL / en), isolated per client and subtree. Students, guardians, change requests and student import are delivered in M3 together with classes.

**Original goal (draft, kept for the M3 plan):** Admins create, list, edit, deactivate and share staff with role assignments and activation emails; create students with generated codes, duplicate detection and linked guardians (siblings share one guardian, portal accounts on request); students edit their own non-critical data and request changes to critical data that staff approve; staff and students (with guardians) are imported from Excel through one all-or-nothing import framework running as background jobs; a daily job expires staff and warns admins beforehand; clients can sign in through their own OpenID Connect / Azure AD provider — all bilingual (ar RTL / en), isolated per client and subtree.

**Architecture:** Same modular monolith as M0/M1 (`Features/<Module>/` + `<Module>Module.cs`; entities in `Lms.Domain/<Module>/`; persistence and services in `Lms.Infrastructure/<Module>/`; contracts in `Lms.Shared` through Lead PRs). M2 adds three kernels that the feature tasks build on: **background jobs** (Hangfire on MySQL, with a job context that replays the enqueuing caller's `ICurrentContext` so global query filters keep working inside jobs), the **people kernel** (one migration with `StaffProfile`, `StudentProfile`, `GuardianProfile`, `StudentGuardian`, `PersonStatusChange`; normalizers; client-wide duplicate finder; account provisioning; a status gate inside `ValidAssignmentQuery`), and the **import framework** (X-06: template → upload → validate job → preview → all-or-nothing commit job → error report). A person is a platform-level `User` plus one per-client profile per kind (staff / student / guardian); the profile's status gates only the role assignments of its own base kind in its own client.

**Tech Stack:** .NET 10, ASP.NET Core minimal APIs + Razor Pages (account pages), EF Core 10 + `MySql.EntityFrameworkCore` (ADR 0001), MySQL 8.4, OpenIddict 7, Hangfire (new), `Microsoft.AspNetCore.Authentication.OpenIdConnect` (new), ClosedXML (pinned by M1 Task 18), MinIO via `IFileStorage`, SignalR notifications (M1), Blazor WebAssembly + MudBlazor 9, xUnit, Testcontainers, bUnit, Playwright; `ghcr.io/navikt/mock-oauth2-server` in docker compose for external-login tests.

## Global Constraints
- **Every M0 and M1 Global Constraint still applies** (by reference: path format, `X-Lms-Context`, Guid v7, utf8mb4, default culture `ar`, explicit permissions per built-in role and `PlatformOnly`, `UnitAccess.CheckUnitAsync` / `CheckClientRootAsync` with 404 for invisible units, ProblemDetails `code` from `ProblemCodes`, `// ISOLATION-BYPASS: <reason>` marker with explicit `OrganizationId` re-applied, no new `DbSet` properties, two `Program.cs` lines per module, one migration per PR with working `Down()`, `AuditableEntity` + `[Audited]` + isolation test per business entity, names 1–200 chars both languages, paging max 200, invitation lifetime 72 h, FE API interface + fake per module, ar/en resource parity, RTL screenshots in `docs/screenshots/pr<N>/`).
- **People isolation shapes.** `StaffProfile`, `StudentProfile`, `StudentGuardian`, `StudentChangeRequest`, `PersonStatusChange`, `ImportBatch`, `ImportRow` are `IOrgUnitScoped` (unit = the person's **home unit**, or the import's target unit). `GuardianProfile` is `ITenantOwned` only and is visible **only through a live `StudentGuardian` row in the caller's scope** (every guardian query starts from `StudentGuardian`; QA checks). `IdentityProviderConfig` and `StudentCodeCounter` are `ITenantOwned`. (`StudentChangeRequest` and `StudentCodeCounter` arrive in M3; `StudentProfile`, `GuardianProfile`, `StudentGuardian` are created in M2 Task 5 as data model only.) `DataProtectionKey` is platform-level (no tenant; class comment says why).
- **Duplicate checks are client-wide** (they must catch a person registered in a sibling subtree): run with `ISOLATION-BYPASS` + explicit `OrganizationId`, return only *which field* collided, and answer 409 `duplicate_person` with extension `field` (`email` | `mobile` | `nationalId`) — never the other record's id, name or unit. Name + date-of-birth matches for students answer 409 `possible_duplicate` with extension `count` unless the request sets `ConfirmPossibleDuplicate = true`.
- **Normalization (stored form):** email trimmed + lower-case; mobile = digits with an optional leading `+`, spaces/dashes/parentheses removed, must match `^\+?[0-9]{8,15}$`; national id trimmed + upper-case, `^[A-Za-z0-9]{5,20}$`; name key (`NameArKey`, `NameEnKey`) = `PersonNormalizer.NameKey(name)`: trim, collapse whitespace, lower-case, remove Arabic diacritics (U+064B–U+0652) and tatweel (U+0640), `أ إ آ ٱ → ا`, `ى → ي`, `ة → ه`. Nicknames ≤ 100 chars; job titles ≤ 150 chars; status reasons 1–500 chars; `DateOfBirth` between 1900-01-01 and yesterday.
- **Login identity:** staff and guardian `UserName` = normalized email; student `UserName` = student code (lower-case) — student accounts arrive in M3 with a default password per D24. Email is the login identity and is **read-only after creation** in M2 (PRD gap G7). Users may have no email (students); uniqueness of email is enforced only when present (`LmsUserValidator`, Task 5).
- **Person status gate (one rule, Task 6):** a role assignment is valid only if the holder's profile *of the role's base kind* in that client is missing (legacy bare user) or `Active` and, for staff, `ExpiresOn` is null or ≥ today. A user who is both staff and guardian keeps guardian access when deactivated as staff. `User.Status` is recomputed from all of the user's profiles (all clients) so the M1 blocked-login messages still work: no profile active anywhere → `Expired` if every inactive profile is expired, else `Deactivated`.
- **Staff expiry:** `ExpiresOn` is the last usable day (inclusive). Access stops at the start of `ExpiresOn + 1` through the status gate even before the job runs; the daily job then sets `Status = Expired` and notifies. Pre-expiry notice once per staff when `today ≥ ExpiresOn − Staff.ExpiryNoticeDays` (resolved at the home unit).
- **Imports (X-06):** `.xlsx` only, ≤ **10 MB**, ≤ **5,000** data rows, first worksheet, header row 1; headers match the column's English header, Arabic header or key (case- and whitespace-insensitive); **create-only** (an existing person is an error, never an update); one transaction for the whole file; side effects (emails, notifications) only after commit; commit re-validates; an uncommitted batch is discarded after **7 days**. Error report = the uploaded columns + a trailing `Errors` / `الأخطاء` column, errored cells filled `#FFC7CE`, rows ordered by row number, messages in the batch culture.
- **Background jobs:** Hangfire, MySQL storage, queues `default` and `imports`, `WorkerCount = 4`. Recurring job ids `staff-expiry` (cron `0 2 * * *`) and `imports-cleanup` (`0 3 * * *`) in the time zone `Jobs:TimeZone` (default `UTC`). Jobs never run with an empty context: per-caller jobs replay the enqueuing caller's context; system jobs run once per client with a system context scoped to that client's root. Dashboard at `/jobs` in Development only. Integration tests use `InlineJobScheduler`; one test proves the real Hangfire wiring.
- **Student code:** **Moved to M3** (D23); the rule is replaced by D25 (one running sequence per client). The revised constraint is in the appendix.
- **External login:** secrets encrypted with ASP.NET Data Protection (purpose `Lms.IdentityProviders.v1`, keys persisted in MySQL) and never returned by any API (`HasClientSecret` only). A session started through a client's provider carries claim `lms_ext_org` = that client's id; contexts of any other client are hidden from the chooser and rejected (403 `OutOfScope`). No auto-provisioning: an unmatched identity sees `external_account_not_found`.
- **New packages** (pinned in `Directory.Packages.props` by the first task that needs them): `Hangfire.Core`, `Hangfire.AspNetCore`, `Hangfire.MySqlStorage` (Task 4; MySqlConnector-based — BE1 verifies MySQL 8.4 support when pinning, fallback `Hangfire.Storage.MySql`); `Microsoft.AspNetCore.Authentication.OpenIdConnect` 10.0.x (Task 21). ClosedXML comes from M1 Task 18 (if not merged yet, Task 7 pins it).
- **Migrations:** `AddPeople` (Task 5), `AddImports` (Task 7), `AddIdentityProviders` (Task 21, includes `DataProtectionKeys`). `AddStudentCodeCounters` (Task 12) and `AddStudentChangeRequests` (Task 18) move to M3. Hangfire creates its own tables (`PrepareSchemaIfNecessary = true`, table prefix `hf_`) — not an EF migration.
- **FE:** API interfaces `IStaffApi`, `IImportsApi`, `IIdentityProvidersApi` in M2 (`IStudentsApi`, `IGuardiansApi`, `IChangeRequestsApi`, `IMyProfileApi` in M3), each with HTTP implementation + fake (`Lms:UseFakeApi=true`). Arabic input fields `dir="rtl"`, English, email, mobile, national id and code fields `dir="ltr"` in both cultures. Dates shown with the current culture (Hijri when `Ui.ShowHijriDates`).

## Review Focus
*After D23 the student/guardian parts of these items (Tasks 13, 14, 15, 18, 20) apply in M3; in M2 they apply to staff, staff import, the people kernel and external sign-in.*
1. **A duplicate or guardian lookup leaks another subtree's data:** a School-2 admin creating a staff member or student whose email / mobile / national id exists in School 1 must get 409 with only `field` (no id, name, unit); guardian match returns only name and masked mobile; a School-2 admin opening a School-1-only guardian or student by id gets 404. (Tests in Tasks 5, 10, 13, 14; probes in Task 34.)
2. **Cross-tenant takeover through an external provider:** client A's provider must only link people who have a profile in client A, and a session started through it must never open a client-B context even for a user who belongs to both. (Tests in Task 22; E2E in Task 38.)
3. **Import is not really all-or-nothing:** a failure on the last row (or a duplicate created by someone else between preview and commit) must leave no users, profiles, assignments, guardians, code-counter increments or emails; a double click on Commit must commit once. (Tests in Tasks 7, 17, 20.)
4. **Deactivated or expired people keep access:** a deactivated staff member with a live token, or one whose `ExpiresOn` was yesterday and the job has not run, must be refused on the next request; a teacher who is also a guardian keeps guardian access after staff deactivation; reactivation restores access. (Tests in Tasks 6, 11, 19.)
5. **Role-blocking policies bypassed on a side path:** `CreateTeachers` / `CreateAdmins` at a unit must block assigning those roles through the assignments API, staff create, staff share **and** staff import; `CreateStaff` / `CreateStudents` must block create **and** import. (Tests in Tasks 8, 10, 16, 17, 20.)
