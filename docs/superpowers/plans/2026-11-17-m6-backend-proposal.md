# M6 Backend Proposal: Communication (email, SMS, push, messaging, announcements, moderation)

> **Status: DRAFT proposal for the Team Lead (no code), revision 5 (2026-11-18), after QA2's re-review and the owner's decisions D66-D69 (sections 17 and 18 answer the two re-reviews and mark every question the owner has settled); revision 3 answered QA2's first review in section 16.** Written by Backend 1 from `docs/DEV-PLAN.md` M6, `docs/PRD.md` FR-NOT-01..03, FR-MSG-01..04, X-07, §3.4 and D1-D57, and the code on `main` at `3fb28bda` + the M4a/M4b notification, forum and job seams. Modelled on the M4b backend proposal (#427). The numbered **Q** items in section 13 are **settled by D66-D69** (section 17 lists which); sections 2 to 12 are built on those decisions.

**Goal:** Every domain event reaches people on the channels they chose (in-app always; email, SMS and Web Push per event and user preference) through one queued, retried, rate-limited delivery pipeline; users hold 1:1 and group conversations under client-level messaging rules; staff publish targeted announcements (organization, unit, class, course, group or role; now or scheduled; pin; expiry); users report messages and block others, and admins moderate.

**Spec:** FR-NOT-01/02/03, FR-MSG-01..04, X-07, §3.4 (Messaging/announcements row), §4.4 feature flags (`Messaging`, `GuardianPortal`), D16/D28 (role escalation), D30 (guardians), D42 (relationship rules), D51 (kernels), D52/D56 style decisions. Master plan: `docs/DEV-PLAN.md` M6 items 1-5 (email + preferences; SMS + push; messaging; announcements; moderation).

## 2. Decisions this proposal assumes (confirm in review; see section 13 for the owner questions)

1. **One pipeline.** In-app stays synchronous (as today); email, SMS and push are **asynchronous deliveries from a transactional outbox** (the pattern of ADR 0004): the `DeliveryOutbox` rows commit with the event, a dispatcher sends them, a failure never undoes the event and a crash never loses a delivery.
2. **At-least-once delivery with idempotent sends.** A delivery is claimed with a lease, marked `Sent` with the provider message id, and a retry after a crash may duplicate at most one message; the provider message id is stored so duplicates are visible. No exactly-once claim.
3. **Providers are abstractions with fakes** (`IEmailProvider` over the existing MailKit sender, `ISmsProvider`, `IPushProvider`); the concrete email relay (D67) and the Saudi-licensed SMS gateway (D68) are chosen before go-live, so every provider is built behind its interface with a development fake now; the fakes are what every test and the E2E stack use.
4. **No per-client provider credentials in v1** (like Zoom, D49): one platform email relay, one platform SMS account, one VAPID key pair, from server configuration/secret store only. Per-client sender name/branding is a setting (Q12).
5. **Preferences are per user, per event, per channel** (existing table) with **catalog defaults** and **mandatory events**; a client admin sets *which channels may be used at all* for the client (setting), a user can only narrow.
6. **Quiet hours apply to SMS and push only**, never to email or in-app, and never to mandatory/urgent events (Q5). They are evaluated in the client's time zone (`Jobs:TimeZone` today; a unit setting is Q5b).
7. **Messaging is relationship-based, not unit-subtree-based.** A conversation is tenant-owned (`OrganizationId`) and visible only to its participants; org admins do **not** read arbitrary conversations (moderation sees reported messages only, section 8).
8. **Rules are default-deny with an editable matrix per client** (FR-MSG-02), evaluated on conversation creation, on adding a participant and on every send to a direct conversation; student-to-student is off by default.
9. **Announcement audiences are resolved server-side at publish time** into a recipient snapshot (so history is stable), reusing the M3 relationship rules for *who may target what* and the existing role/enrollment/group queries for *who is reached*.
10. **Moderation never exposes whole conversations**: a report carries the reported message plus a bounded context window; moderators act on messages and on a user's messaging right, all audited.

## 4. Delivery pipeline (FR-NOT-03, X-07)

### 4.1 Write path
`INotificationPublisher.PublishAsync` (unchanged signature) keeps validating the event and resolving recipients, then in **one transaction**: inserts the `Notification` rows (in-app) and, for each recipient and each channel in `{Email, Sms, Push}` that passes the checks below, one `DeliveryOutbox(Pending)`. Checks, in order: client channel setting on (`Comms.EmailEnabled`/`SmsEnabled`/`PushEnabled`); the user's preference for (event, channel), falling back to the catalog default; the event is not `InApp`-only; a contact point exists (otherwise **no row**, counted in a metric); the address is not suppressed (`Suppressed` row kept for the log). The in-app SignalR push stays after commit as today.

### 4.2 Dispatcher
A recurring system job (`comms-dispatch`, every 15 s, also kicked after a publish) claims a bounded batch **per channel** with a conditional update (`Status=Pending AND NextAttemptAtUtc<=now` → `Sending`, `LeaseUntilUtc=now+2 min`, ordered by `NextAttemptAtUtc`, `LIMIT n`), so two nodes never take the same row; expired leases return to `Pending`. For each row it loads the notification, renders the channel text (4.4), calls the channel sender through the limiter, and writes the outcome. It runs under the system context and reads across clients: **bypass site 1** (allow-listed, with the isolation statement: it reads delivery rows and the minimum of user contact data, never content of other modules).

### 4.3 Retries and failure classes
Provider results are typed, never string-matched in the dispatcher (`DeliveryResult`: `Accepted`, `Transient`, `Permanent`, `NotConfigured`): `Transient` (timeout, 5xx, 429): retry at `base * 2^(attempt-1)` with **base 30 s, jitter ±20 %, cap 1 h**, a provider `Retry-After` wins when longer; **attempts or window per channel** (email 8 attempts or 24 h, SMS 4 attempts or 2 h because a late code is worse than none, push 5 attempts or the event TTL); `Permanent` (invalid address, 4xx, rejected sender): `Failed`, no retry, and for a **hard bounce** or complaint a `ContactSuppression` is written; `NotConfigured`: the delivery stays `Pending` with a long backoff and the provider status shows it (the Zoom `provider_not_configured` pattern). `LastErrorCode` stores a code, never a response body, an address or a token. Each row carries an `ExpiresAtUtc` (the channel and event TTL); an expired row becomes `Expired` (the `Skipped` status in section 3), not sent. **A hold never expires a row:** when quiet hours or a cap put a row in `Held`, `HeldUntilUtc` is set and the TTL window **starts when the hold ends** (`ExpiresAtUtc = HeldUntilUtc + window`), so an SMS held overnight goes out at 07:00 and is not lost; only a message that is stale by nature (an announcement that expires before the hold ends) becomes `Expired` with the reason code `expired_while_held`, counted and shown to admins. **Urgent and mandatory events bypass both quiet hours and caps** (never `Held`). Tests: `Held_sms_is_not_lost_by_quiet_hours`, `Cap_overflow_is_sent_the_next_client_day`, `Urgent_event_ignores_quiet_hours_and_caps`. The dispatcher is **per client** under a per-client `IJobKeyLock`, with per-client fairness so one client's broadcast cannot starve the others.

### 4.4 Templates
Each (event, channel) has a localised template in **resource files** (ar and en; the existing `NotificationText` parity rule) rendered with the stored parameters: email = subject + HTML + text alternative, SMS = one short text (length-aware: Arabic uses UCS-2, 70 characters per segment, the renderer reports segments and truncates with an ellipsis at a configurable cap), push = title + body + a deep link. The recipient's language is the user's preference if set, else the unit's `Ui.DefaultCulture` (Q10). Templates never carry data the recipient could not see in the app (no grades in SMS/push bodies by default; a "new grade" push says so without the score, Q3).

### 4.5 Rate limits and caps
Per provider token bucket (email relay messages/second, SMS gateway messages/second, push), a penalty window on a provider 429, a bounded in-memory queue, and **per-client daily caps** as settings (`Comms.MaxEmailPerDay` default 5,000, `Comms.MaxSmsPerDay` default 500, `Comms.MaxPushPerDay` 20,000): over the cap a delivery becomes `Held` until the next UTC day and the unit admins get one `Comms.CapReached` notice per day. Caps count **sent** deliveries, mirroring `Live.MaxCreatesPerDay`; **the day is the client's day** (its time zone, not UTC), so "held until tomorrow" means 00:00 local. **Per-recipient limits** (counted in the outbox per user, channel and client day): defaults email 20, SMS 5, push 50 (`Comms.MaxEmailPerUserPerDay`, `Comms.MaxSmsPerUserPerDay`, `Comms.MaxPushPerUserPerDay`); email and push over the limit are `Held` to the next day and collapsed to one deferred "you have N updates" row per channel, SMS over the limit is `Skipped` with the code `recipient_cap` (counted, shown to admins) so one chatty thread can never run up SMS cost on one person; mandatory events are exempt. **Per-author announcement cap:** `Announcements.MaxPerAuthorPerDay` (default 10; organization-wide targets only for roles that hold them); over it is 429 `rate_limited` with probe rows. Tests: `Per_recipient_daily_cap_holds_the_overflow`, `Announcement_author_cap_returns_429`. A broadcast announcement larger than the remaining cap does not silently drop recipients: the overflow is `Held` and delivered next day (Q9 asks whether to refuse instead).

### 4.6 Retention
`DeliveryOutbox` rows older than **90 days** (`Comms.DeliveryRetentionDays`) are deleted by a daily job; `ContactSuppression` is kept until the user changes the address or an admin lifts it. Delivery rows hold no message body, so retention is about volume, not privacy (Q11 confirms the period).

### 4.7 Bounces and complaints
v1 logs what the SMTP exchange itself reports (synchronous rejections) and accepts **asynchronous bounces** through one anonymous, signature-verified webhook for the chosen relay (`POST /api/integrations/email/events`, the Zoom webhook pattern: body cap 256 KB, signature over the **raw bytes** in constant time, 5-minute timestamp window, per-IP failure limit, receipt and effect in one transaction, a duplicate is a 200 no-op only after verification); the exact payload depends on the relay (Q1). Probe rows in Task 16: bad/missing signature 401, stale 401, oversize 413, repeated failures 429, valid event 200 once, duplicate 200 without a second effect. Without a webhook relay, bounces arrive by a polled mailbox (VERP return path) in a later task.

## 5. Provider abstractions with fakes

```csharp
public interface IEmailProvider { Task<DeliveryResult> SendAsync(EmailDelivery d, CancellationToken ct); }          // wraps IEmailSender (MailKit)
public interface ISmsProvider  { Task<DeliveryResult> SendAsync(SmsDelivery d, CancellationToken ct); string Name { get; } }
public interface IPushProvider{ Task<DeliveryResult> SendAsync(PushSubscription s, PushPayload p, CancellationToken ct); }
public abstract record DeliveryResult;   // Accepted(ProviderMessageId), Transient(Code, RetryAfter?), Permanent(Code, HardBounce?), NotConfigured
// BE2's delivery-provider draft (docs/superpowers/plans/2026-11-15-m6-delivery-providers-draft.md, branch be/m6-delivery-draft) is the detailed source for this section
```

- **Fakes** (`FakeEmailProvider`, `FakeSmsProvider`, `FakePushProvider`) in Infrastructure, registered in the test host (the `FakeMeetingProvider` pattern: recorded calls, scripted outcomes `ScriptNext(Transient, Sent, …)`, `FailAfter`). The E2E stack uses them too, plus a Development-only trigger like `POST /api/dev/zoom/events` (`/api/dev/comms/outbox` to list what was "sent").
- **Real providers:** email = the existing `SmtpEmailSender` (MailKit) behind `IEmailProvider`; SMS = a real adapter written when the owner has chosen the gateway before go-live (D68), the fake until then; push = a VAPID implementation (`WebPush` library or hand-rolled RFC 8291/8292 with `System.Security.Cryptography`; decision in the task, library license checked).
- **`IContactResolver`:** `user → (email, mobile, push subscriptions, verified flags, language)`. Email from `User.Email`; mobile from `StaffProfile.Mobile`, `GuardianProfile.Mobile`, or the student record's mobile if present (D26: students may have none); for a **student under the minor rule** (Q6) SMS/email resolve to the primary guardian's contact, flagged `OnBehalfOf`. Missing contact = no delivery row.
- **Provider status** (`GET /api/comms/provider-status`, `Comms.Manage`, platform health only: configured/healthy per channel, never configuration), like the Zoom status.
- **Secrets** (SMTP password, SMS credentials, VAPID private key) only in configuration/secret store; a test asserts none appears in logs, DTOs, audit rows or delivery rows.

## 6. Messaging (FR-MSG-01/02)

1. **Conversations:** `POST /api/conversations` (direct with one user, or group with ≥2 others); a direct conversation between the same pair is **returned, not duplicated** (`DirectKey`): the call answers **200 with the existing conversation**, never 409 `conversation_exists` (it leaks nothing; #612 is told to expect 200). **Groups under D69:** only staff create a group (Teacher, Counselor, Supervisor, Manager, Org Admin; `Student_cannot_create_a_group`, a guardian neither); max size `Messaging.MaxGroupSize` (default 50, D66). **The check on create and on add is owner to member, never pairwise** (the owner must be allowed to message each member under the rules; members are not checked against each other, so a group of students can exist). The member list is visible to every member. **Students may post only in a class or course group a teacher created**; any other staff group has staff posters and read-only students, and a teacher or a moderator can set any group **read-only** (403 for posting students, tombstone-free). Students in a staff group **cannot open a direct conversation with each other** (the direct rule applies to the pair as always): test `Students_in_a_staff_group_cannot_open_a_direct_conversation_with_each_other`; an Org Admin or Manager **cannot add a student to a private group of two** (a group with fewer than three members is a direct conversation by another name): test `Admin_cannot_add_a_student_to_a_private_group_of_two`. Participants may leave a group; the owner may add or remove (rules re-checked on add).
2. **Rules (`IMessagingPolicy`):** `CanMessageAsync(senderUserId, recipientUserId)` combines (a) the client's `MessagingRule` matrix by the two users' **active built-in roles** (a user with several roles: any allowed pair), (b) the **relationship** when the rule says `Relationship`: sender and recipient share a ClassCourse (teacher of / enrolled in), or the recipient is a guardian of a student the sender teaches or counsels (M3 links), (c) blocks, (d) `MessagingRestriction`, (e) the `Messaging` flag. Defaults (Q13, safeguarding-first, agreed with #612 and #615): **no role reaches a student without a relationship**. Teacher ↔ own students, those students' guardians and staff of the unit; Counselor and Supervisor ↔ students and guardians **they counsel or supervise** (relationship) and staff; Manager and Org Admin ↔ staff and guardians, and **students only through a group or an announcement** (an admin cannot open a private conversation with a student by default); Student → own teachers and counselor, **never other students**; Guardian → teachers and counselor of own children, not other guardians. A failing check is 403 `messaging_not_allowed` with a reason code, never a user list. **A client may only narrow the D69 defaults (D69: the Org Admin may tighten per client):** `PUT /api/comms/messaging-rules` is validated against the default matrix and refuses (400 `rules_looser_than_default`) any cell the defaults deny: student-to-student, an admin or manager private conversation with a student, guardian-to-guardian, and a guardian reaching staff who do not teach or counsel their child. Test `Rules_cannot_be_loosened_below_the_defaults` (every denied cell, one by one, plus a tightening that is accepted and a restore to the defaults). **"Narrower" is defined by one order on the rule's `Via`: `NotAllowed` < `Relationship` < `SameUnit` < `Anywhere`.** A cell is refused (400 `rules_looser_than_default`) when its `Via` is **above the default of that cell on this order**, not only when the default is `NotAllowed`: a client cannot turn Teacher to Student from `Relationship` into `SameUnit` or `Anywhere` (a teacher reaching any student of the school), nor widen any allowed cell. **Second enforcement point:** `IMessagingPolicy` evaluates `min(stored, default)` for every cell on every call, so a stored row written by an older version or edited directly in the database can never loosen anything; test `Policy_ignores_a_stored_rule_looser_than_the_default`. **A user with several roles:** each role pair brings **its own** relationship requirement and the best pair wins, never a mix (an Org Admin who is also a Teacher reaches students only as a Teacher, that is only students they teach; test `Admin_who_is_also_a_teacher_reaches_only_their_own_students`).
3. **Messages:** `POST /api/conversations/{id}/messages` (text + up to 5 attachments via the asset path, same file rules and sanitising as M4a), paged `GET` (keyset by id, newest first), **no edit in v1**; the sender may **delete their own message for everyone within `Messaging.DeleteWindowMinutes` (default 15)**, shown as "Message deleted" (a tombstone keeps the reporter context; #612's "delete for me" is dropped and #615's menu already matches); a removed message's original text stays visible to moderators only, for the retention in Q11/Q12. Server time on every timed DTO. **Deleted or expired accounts (D66):** the messages of a user whose account was deleted or expired stay in the conversation (retention as listed), and the sender is shown with a neutral name ("Former user" / "مستخدم سابق") and no profile link; the user can no longer send, and the conversation stays readable to its other participants.
4. **Unread counters and receipts:** `LastReadMessageId` per participant (no per-message receipt rows); `POST /api/conversations/{id}/read`; the conversation list returns `UnreadCount`, `LastMessage`, `Muted`. **Read receipts are optional** (FR-MSG-01): a client setting `Messaging.ReadReceipts` (default off; Q16) controls whether other participants see "seen by"; counters work either way.
5. **Search:** MySQL FULLTEXT (`WITH PARSER ngram` for Arabic and English) on `Message.BodyText`, **always joined to the caller's participant rows** (a user searches only conversations they are in); minimum query length 2, result cap 50, rate limited, **a hard window** (the first 200 hits per query, keyset paging inside it) and a **conversation filter required beyond page 1**, so search cannot be used to enumerate message volume. The ngram parser's quality for Arabic stems is a risk (section 12); fallback is `LIKE` on a short window.
6. **Realtime:** a new message publishes `MessageReceived{conversationId, messageId}` over `NotificationsHub` to each participant's user group (**ids only, never text or the message DTO**: the client fetches the message through the participant-checked route, so the event cannot leak content; #612 C4 changes to a fetch); an in-app notification `Messages.NewMessage` is created **only for offline/muted-not users and is throttled per conversation** (one unread notification per conversation until read, so a chatty thread does not flood the bell or the outbox); email/push for messages follow the same throttle and preferences, SMS never for chat by default.
7. **Blocks:** `PUT/DELETE /api/me/blocks/{userId}`; a block hides nothing already sent, stops new direct messages both ways, and does not remove either from shared groups (Q14). **Rule: a block belongs to its owner.** No moderation or admin route can create, read or delete a `UserBlock`; the "People blocked" tile of #615 §7.6 means the moderators' `MessagingRestriction` list, never user blocks. Test: `Moderator_cannot_remove_a_user_block` (every moderation route, 403/404, row unchanged).

## 7. Announcements (FR-MSG-03)

- **Create:** `POST /api/announcements` with `TitleAr`/`TitleEn` (both), body ar and/or en (sanitised), up to 5 attachments, 1..n targets (`Organization`, `Unit` (+`IncludeSubtree`), `Level`, `Class`, `ClassCourse`, `Group`), `RoleFilter` chips (`Staff`/`Students`/`Guardians`), `PublishAtUtc?` (null = now), `ExpiresAtUtc?`, `IsPinned`, `Notify`. `Draft` saves without sending. `PUT` edits while `Draft`/`Scheduled`; once `Published` only expiry/pin/withdraw change (body edits create a visible "edited" marker, Q19).
- **Who may target what:** needs `Announcements.Manage` at the **authoring unit** (UnitAccess) and the target inside the author's scope: a `Unit`/`Class`/`Organization` target must lie at or below a unit where the author holds the permission; a **Teacher** (relationship rule `OwnClassCourses`) may target only own ClassCourses and their groups and may not use `Organization`/`Unit`/`Level`/`Class`; a target the author may not reach is **404, never 403**, so existence is not revealed (`Teacher_cannot_target_a_class_course_they_do_not_teach`); Manager/Supervisor/Org Admin per the matrix (Supervisor: supervised courses' ClassCourses). Anything outside is 404 for a hidden target, 403 for a missing permission.
- **Audience resolution (`IAudienceResolver`)** reuses existing queries, nothing new in the model: `Organization`/`Unit` = active role holders and active students at/below the unit (the `NotificationRecipientResolver` shape + `ClassStudent` placements); `Class` = active class students; `ClassCourse` = active `CourseEnrollment`s; `Group` = `GroupMember`s; `Role` = valid role assignments at/below the unit (`ValidFrom/To` honoured, inactive users excluded). The `Guardians` chip adds the **linked guardians with a portal account** of every student reached (D30), once each (the former `IncludeGuardians` flag is this chip); `Staff` and `Students` narrow or widen the same way; `Level` = every active class of that level type under the author's scope. The result is deduplicated and snapshotted into `AnnouncementRecipient` by the publish job in batches of 500 (large audiences never run inside the request). **Bypass site 2** (allow-listed): the resolver reads people across units below the author's scope boundary only through these queries, client-matched and live-only.
- **Publish job:** `Publish` kicks `announcement-publish:{id}` (or schedules it at `PublishAtUtc` through the keyed scheduler, moved on edit, cancelled on withdraw); it resolves, writes recipients, then publishes **one** `Announcements.Published` event per batch of recipients through the normal publisher (so channels, preferences, quiet hours and caps all apply). Expiry: `announcement-expire:{id}` flips the status and hides it; pinned announcements sort first.
- **Reading:** `GET /api/me/announcements` (paged, active, pinned first, unread flag), `POST …/{id}/read`; `GET /api/announcements` (authors/admins: by status, with `AudienceCount`, delivery summary counts per channel). `GET /api/announcements/audience-preview` returns the **count** (and a capped sample of names for the author's own scope) before publishing.
- **Course board interplay (D66: one announcements store with ar+en titles):** `Announcement` is the single store. Until the board is moved, `CourseAnnouncement` keeps working and the course announcements page lists **both** what the caller may see (its own board posts and the ClassCourse-target announcements, one read-only merged query, each marked with its source). The board's rows migrate onto `Announcement` in a later task (a data migration with an `ar` title copied from the body's first line and an `en` title equal to it when only one language exists; the board endpoints then answer from the new store and the table is dropped one release later). New course posts made after that task are announcements with a ClassCourse target.

## 8. Moderation (FR-MSG-04)

- **Report:** `POST /api/messages/{id}/report` by any participant (not the sender), once per (message, reporter); stores the reason code, optional note, the **frozen context window** (the reported message and the 5 before and after, text only) and `MessageReportUnit` rows = **the units that may moderate it**: the unit of the conversation's context when it has one (`ClassCourseId` → the class course's unit), otherwise **every unit where the sender holds an active assignment or profile** (a teacher in two schools, a guardian of children in two units: all of them), and the client root when none is found, so a report is **never invisible to every moderator**; an Org Admin at or above any of those units sees it (the matrix's "Moderate"), a client-root admin sees all. Tests: `Report_is_visible_for_a_sender_with_two_units`, `Report_with_no_unit_falls_back_to_the_root`. The reporter is told it was received; the sender is not told who reported.
- **Queue and review:** `GET /api/moderation/reports` (`Messaging.Moderate`, scoped by `MessageReportUnit`, status filter, `?stats=` counts per status for the dashboard tiles in `GET /api/moderation/stats`), `GET …/{id}` (the frozen context; never the live conversation), `POST …/{id}/resolve` with **one action set for all three documents**: `Dismiss` (UI: Keep; bulk dismiss allowed), `Remove` (the message becomes a tombstone for participants; its original text stays for moderators only), `Warn` (a `Messaging.Warning` notice to the sender), `Restrict` (a `MessagingRestriction` with an end date; the sender is told, never who reported), `RemoveAndRestrict` (UI: Remove and block sender), `LockConversation`. Statuses: `Open` → `InReview` → `Dismissed` | `ActionTaken`. Every action is audited and notifies the reporter with the outcome code only.
- **Blocking** is the user-side tool (section 6.7); reporting and blocking are independent.
- **Privacy rules:** no endpoint lists or reads another user's conversations; moderators see only reported context; a moderation read is itself an audit entry; platform admins have no extra read path. Retention of reported context follows the report (Q21).
- **Abuse limits:** per-user send rate (`Messaging.MaxPerMinute`, default 30), per-user daily new-conversation cap (`Messaging.MaxNewConversationsPerDay`, default 50), report rate cap, attachment type allow-list, body length cap; over a limit is 429 `rate_limited`.
