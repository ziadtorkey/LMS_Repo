# Spike S1: the gradebook grid (M5 Task 24)

**Question (M5 plan S1, FE proposal H3/H4):** can a Blazor WebAssembly page render a class gradebook (60 students by 25 items) as a real `<table role="grid">`, re-render one row when one score changes, and keep one roving tab stop, without virtualising?

**Answer: yes, with a per-row component and a `ShouldRender` guard. No virtualisation is needed up to the server's page size of 50 to 100 students.**

## What was measured

The measurements are `tests/Lms.Client.Tests/Gradebook/GridSpikeTests.cs` (bUnit, run on a developer laptop; they are guards, not benchmarks). A real-browser (Playwright) run with 60 by 25 cells was **not** done in this task: the standalone fake serves 3 students, and the editing keys that make a cell edit worth measuring arrive in Task 25. That run belongs to Task 25's spike close-out, with the keyboard model.

| Case | Result (bUnit) |
|---|---|
| First render of 60 rows x 25 items (1500 `GradeCell`s, 5 category groups, 60 rows) | about 70 ms |
| One row replaced (a score saved) **with** the guard | 1 `GradeRow` of 60 re-renders, about 30 ms |
| The same change **without** the guard (first version of this task) | 60 of 60 rows re-rendered, about 690 ms |
| The page reordered (a sort or a page change), rows keyed by student id | the 60 rows are moved, not rebuilt; each renders once more because its row position (the key map's coordinates) changed |

## How the rows skip rendering

- `GradebookGrid` renders `GradeRow` per student with `@key="Rows[i].StudentId"`.
- `GradeRow` overrides `ShouldRender` and re-renders only when its row (by reference), the category layout (by reference), the decimal places, its position, the focused column, the open menu column, the cell being edited, or the edit session's stamp for this student changed.
- **The trap:** the snapshot of the first render must be taken in `OnInitialized`, where the parameters are already set. Taking it inside `ShouldRender` makes every row look changed on the first update after the initial render, which defeats the guard once (60 renders after the first edit) and is easy to miss. This is what the first version did; the test `Changing_one_row_re_renders_that_row_only` now guards it.
- The page builds the category layout (`CategoryGroup.From`) **once per loaded gradebook** and passes the same list to every row, so the reference check is meaningful. A new load (a page change, a save) produces new objects only for what the server changed if the client replaces just that row (Task 25's optimistic save does exactly that).
- The row's `EventCallback` parameters are not part of the check on purpose: they are recreated on every parent render and carry no data.

## Roving tabindex

- The first cell of the first row has `tabindex="0"`; every other cell has `tabindex="-1"`. Tab therefore enters the grid at one stop and leaves it at the next Tab, which is the WAI-ARIA grid pattern (test `Only_the_first_cell_is_a_tab_stop_whatever_the_size`: 1 stop, 1499 `-1`).
- **Task 25 result (real browser, Playwright against the standalone client):** arrows, Home, End and Ctrl+Home move the stop and the focus; Enter puts an input in the cell and focuses it; typing then Tab saves and moves right (the server value is shown); Shift+F10 opens the menu with the first item focused, the arrows move between items and Esc closes it and returns the focus to the cell; Tab in navigation mode leaves the grid for the next control; the page does not scroll on any of these keys.
- **How it is split:** the key map is pure C# (`GridKeyboard.cs`, tested without a browser); the Blazor grid calls it from a keydown handler on each cell; `gradebook-grid.js` (about 40 lines, focus only) stops the default of exactly the keys the map handles (it reads `data-mode` on the table: navigation or edit) and moves the browser focus to the cell .NET chose. Every column (items, category results, Final, Band) is a gridcell, so all of them can be reached.
- **Cost:** a keypress that moves focus renders two rows at most (the one losing and the one gaining the tab stop); typing in a cell renders none (the draft is held in the session; the input already shows it); a save renders that student's row only.

## Paging, not virtualising (S2)

The grid asks the server for 50 students per page (`GradingLimits.GridPageSize`) and shows a pager when there are more (`Pages_students_by_50`). A university section of 200 students is therefore 4 pages of at most 50 x 25 cells, well inside the measured budget; the row count is limited by the server, so virtualisation would add a second scroll model (and break sticky headers and the focus ring) for no gain.

## One layout per size (L19)

Below 600 px the page renders the student-first list **instead of** the grid; the grid is not in the DOM. The `IViewport` service answers from a `matchMedia` query and raises `Changed`, so a rotated phone swaps the layout. Anything typed in the phone layout before a swap must survive it; that is Task 25's job once there are inputs (the draft state will live in the page, not in either layout).

## Costs and risks found

- **Re-render storms** are the main risk, and are cheap to cause: any parameter that is a new object on every parent render (a new list, a lambda that captures per-row data) re-renders every row. Pass stable objects and keep per-row data on the row.
- **Sticky edges and focus:** `lms-gb-wrap` carries `scroll-padding` (the two header rows and the student column) so a focused cell is never under a sticky edge (WCAG 2.4.11). To be checked in LTR and RTL with the key map in Task 25.
- **No client arithmetic:** the grid shows `FinalPercent`, `CategoryResults` and the band exactly as the server sent them (`Final_comes_from_the_response` feeds a final that no arithmetic on the cells could produce).
